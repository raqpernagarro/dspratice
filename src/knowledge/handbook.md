## Why AI-ready, not AI-generated

AI-generated means an AI produced the system’s artifacts. AI-ready means the system is structured so that AI-generated output stays on-system. Don’t conflate them when you talk about maturity.

### The distinction

| AI-generated | AI-ready |
| --- | --- |
| A model drafted components, tokens or docs. | Tokens, metadata, constraints and documented anti-patterns exist so a model cannot go off-system. |
| Quality depends on the prompt. | Quality depends on the contract: closed vocabulary, absences, rules, evals. |
| Nothing stops the next generation from drifting. | Checks in CI and a release eval stop drift and invention before they merge. |

### What “readable by agents” means in practice

- Every Figma value has a code name (codeSyntax). Agents never name things themselves.
- Every component says when to use it, when not to, and its anti-patterns, as data, not prose in a description box.
- A list of absences: names agents keep inventing that do not exist, published to every channel.
- A closed vocabulary: “pressed” is not a state, “active” is.

## The system contract

The system contract is one small file in the client’s repository. It describes the design system so that people and tools read the same thing: its tokens and what each one is for, its components and how to use them, the rules the checks apply, names that must not be invented, the Figma link, and which side leads for each part.

### Which side leads, part by part

When Figma and code disagree, someone has to decide which one is right. Neither is right everywhere, so the contract records it for each part of the system. The client decides this with us when the plan is agreed. A typical result:

| Part of the system | Usually leads | Read from |
| --- | --- | --- |
| Primitive colours | Figma variables | Figma variables export |
| Semantic tokens | Figma variables | Style Dictionary / DTCG JSON |
| Component API | Code | React + Storybook manifest |
| Usage guidance | Contract | MDX + guidance JSON |

### Different names, the same roles

Systems name their tokens differently: --color-background-accent-strong-default, color/background/interactive/primary/pressed, --ds-semantic-color-action-primary-hover. The contract renames none of them. An adapter maps each name to a role; the mapping shows what fits, what needs a decision and what stays specific to one system.

## Token governance and agent trust

Token governance is ownership, versioning and a change-approval process for tokens, not the token values. Agent governance is the same question asked of agents: what may they do on their own?

### Change control

- Every change is a branch and a pull request with checks: parity, accessibility, grammar and collisions, on-system eval, index up to date.
- Approval is the existing review plus CODEOWNERS (as GitHub Primer does with changesets). No second approval system.
- Figma changes go through the plugin’s three-way review: Figma now, at last sync, the system. A version is saved first.

### Trust levels for agents

Per action, not per agent: bind loose fills (auto-fix), write guidance (suggest), rename to contract roles (suggest), change token values (suggest), add or remove components (never). Mechanical fixes apply with undo; anything else waits for a person.

## One source, every channel

Every AI tool wants the system in its own format. Keeping them in sync by hand is the failure mode. The contract generates each format; a merge marks them stale; the publisher regenerates them.

| Channel | Format | Who reads it |
| --- | --- | --- |
| Figma Specs + Make guidelines | Markdown rules | Figma Make, Figma agent |
| Storybook MCP | Component manifest (React only today) | Claude Code, Cursor |
| Claude Design | Repository import | Claude Design |
| v0 / shadcn registry | registry.json | v0, shadcn CLI |
| DESIGN.md | YAML + rationale | Gemini, Stitch, any agent |
| AGENTS.md + skills | Markdown + JSON | Claude Code, Codex, Cursor |

Twenty prompts per tool, scored against tokens, components and rules, with a gate. Not a standard yet; the Spotify Encore team published the pattern. Scores in this demo are illustrative.

## Where this comes from (internal)

This application joins three practice projects into one experience. It copies patterns and data; it does not merge their code.

| Prototyping kit (client work, de-branded) | Figma-first source order, binding-parity gate, meta.json per component, propose → confirm → apply, checks in hooks after every edit | binding-parity.mjs (42 components), lint.mjs, check.mjs, fidelity.js ±1px, 414 variables with code syntax. Client names, keys, fonts and colours are not used. |

### What is simulated here

- GitHub: pull requests, checks and merges happen in local state. Nothing is pushed.
- Figma: reading a file, the plugin’s review and applying changes are reproduced from the plugin’s behaviour. No file is touched.
- Scans: the assessment reads fixtures that describe a fictional messy system, not your repository.
- Agents: the styling agent, prototype agent and patrol agent are rule-based. No model is called.
- Evals: scores derive from the current state so they move believably; they are not measurements.

## How we work together

What happens in an engagement, what we need from your team, and what you keep at the end.

### What happens

- Connect read-only and run the assessment scan.
- Readout: agree what leads for tokens and components, name an owner, choose the first changes.
- Adapt the system to the shared contract. Your names stay; adapters map them.
- First changes as pull requests, reviewed in Figma and code, with checks.
- Publish the AI channels; run the release eval.
- Handover: repository, Figma library, the panel, checks, AI channels, a named owner, a baseline.

### What we need from your team

- Read access to the repository and the Figma file.
- A design-system owner who approves merges and sets agent trust levels.
- Decisions in the readout; about sixty minutes.

### What you keep

Everything lives in your repository and your Figma file. The panel ships inside the repository as a dev dependency. You can run it without us.

See it: the example handover, the assessment report.
