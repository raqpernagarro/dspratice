# DS Configurator — Figma plugin

Moves design-system variables between Figma and the DS Configurator. Runs inside Figma on any paid plan; no REST API, no Enterprise, no AI.

```
Figma ──(1 Export variables)──▶ .variables.json ──(Configurator: Import)──▶ edit
edit  ──(Configurator: Export)──▶ .changes.json  ──(2 Import changes)──▶ Figma
```

## Install

1. `npm run plugin:install` — builds the plugin and copies it to `~/Figma Plugins/DS Configurator/`.
2. In Figma Desktop: **Plugins → Development → Import plugin from manifest…** and pick `~/Figma Plugins/DS Configurator/manifest.json`.
3. Run it from **Plugins → Development → DS Configurator**. After code changes, run `npm run plugin:install` again; Figma picks up the new build next time the plugin runs.

> Why not load `figma-plugin/manifest.json` directly? This repo lives in OneDrive (`~/Library/CloudStorage/…`), and macOS blocks Figma Desktop from reading files there (`EPERM … dist/code.js`). The install step copies the plugin to a local folder Figma can read.

For a team, publish it privately to your organization (Organization/Enterprise plans) or unlisted to the Community; otherwise share this folder and repeat step 2.

## Use

**1 · Export variables** saves `<file>.variables.json`: every collection, mode, variable, alias, description and brand-extension override. It also saves the anatomy of every component set: which variable every variant's layers are bound to (the configurator and `npm run ds:parity` read it). In the configurator, **Import** loads it; the editor then runs on that file. The same file feeds code generation:

```bash
npm run figma:sync-from-file -- path/to/<file>.variables.json
```

**2 · Import changes** loads a `.changes.json` exported from the configurator and lists every change before applying:

- **Primitives**: created only when no existing primitive has the value.
  - Colors are grouped by hue (`colors/sky/600`); tinted greys get classic grey names (`colors/slate/200`). A name already used by a hand-made palette gets a separate family (`teal-2`), so curated palettes are never mixed with generated steps.
  - Translucent colors link to their base color and an opacity primitive: `colors/neutral/950/alpha/80` = `colors/neutral/950` at `opacity/80`.
  - Sizes follow the file's naming (`scale/325` = 13px).
- **Values**: tokens re-pointed or set per mode, tagged with where they came from (*Theme · Color*, *Variables table*, …).

- **Components**: component overrides from the configurator's Components tab.
  - The token is created, or updated, in the `components` collection (e.g. `button/radius/md → shape/radius/full`).
  - Then the matching layers are bound to it: every variant of that size, or that type and state.
  - Only layer properties bound to the token being replaced are rebound. Hand-set values are never touched.
  - The preview lists how many layer properties and variants each override affects.

- **Cleanup**: primitives the configurator generated earlier that nothing points at after this import. Only primitives whose description says *Generated by DS Configurator* are ever offered.

Untick anything you don't want, then **Apply selected**. A version (*Before DS Configurator import*) is saved first, so one step in the file's version history undoes the whole import. Importing the same change set twice changes nothing the second time.

## Matching rules

- Collections, modes and variables are matched **by name**, never by id, so a change set applies to any file that follows the token spec (`docs/Tokens-semantic-v2.xlsx`).
- Brand extensions are addressed by their collection name (e.g. *Violet Brand*); a value there becomes a brand override.
- Problems (missing collection, mode, variable or alias target) are listed and skipped, never guessed.
